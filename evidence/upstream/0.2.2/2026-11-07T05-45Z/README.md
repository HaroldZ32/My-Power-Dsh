## 3. `presets/mpd.patch.yml` — what `preset-conformance` DEMANDED, and why

First run against the installed 0.2.2-rc.1 (`preset-conformance-022.log`) FAILED the mount:

```
sessionCreate ok=false → agent-preset/invalid: tool-subagent-list-agents
  (@deepseek-ai/dsh-tool-subagent-control/list-agents): never started
```

Two independent causes, both established from the installed packages:

1. **0.2.2 removed the `./list-agents` subpath export.**
   `@deepseek-ai/dsh-tool-subagent-control@0.2.1-rc.5` exports `"."`, `"./list-agents"`,
   `"./list-agents/locale/*.json"`, …; at `0.2.2-rc.1` only `"."`, `"./src/*"`, `"./package.json"`,
   `"./locale/*.json"` remain — the ROOT plugin now registers `list_agents` itself (string present in
   `0.2.2-rc.1`'s `lib/index.js`, absent from `0.2.1-rc.5`'s). The 0.2.2 `standard` preset dropped the row.
   ⇒ the row was removed from our preset (keeping it is fatal on 0.2.2 and a parity `extra`).
2. **0.2.2 promotes `tool-plugin-manager` from `disabled: true` to
   `disabled: !!js "!ctx.get('profileContext')"`.** Our preset shipped `disabled: true`, which the parity
   rule reads as "the mpd preset does not mount an active reference row". ⇒ the guard was mirrored
   VERBATIM from the shipped `standard` preset. On 0.2.1 no `profileContext` service exists, so the same
   expression evaluates to disabled — the older host keeps its previous behaviour (and the 0.2.1 boot
   below proves the expression evaluates there).

**DECLARED BOUND (capability delta on the older host):** with the row gone, `list_agents` is NOT mounted
on 0.2.1-rc.5 (its root plugin does not register it). MOUNTING on 0.2.1 is unaffected — proven below.

### The 0.2.2 boot red — ROOT CAUSE (a Blocker for T3, not a note) — **REPAIRED under T7**

> **UPDATE (T7, same evidence dir):** this Blocker was repaired by making the adapter's `executeTool`
> shape-adaptive. After the repair BOTH bundle-lifecycle arms are GREEN (`exit=0`,
> `[roles-probe] ADAPTER_TOOL_CALL=ok` on 0.2.2-rc.1 AND 0.2.1-rc.5). Full record:
> `T7-adapter-tool-batch.md`. `dist/**` remains the integrator's to rebuild — the repair's source is in
> `packages/mpd-dsh-adapter-plugin/src/index.ts`, and the adapter dist was restored byte-identically
> after the proof.

`[roles-probe] ADAPTER_TOOL_CALL=fail:Tool batch execution failed` — the QA probe calls
`dsh.executeTool({ name: "mpd_config_get", arguments: {} })`, and the adapter forwards it to the harness's
`ToolsService.execute`. That API changed contract at 0.2.2:

- **0.2.1-rc.5**: `execute(exec: ToolExecutionInput)` — ONE call `{ callId, name, arguments, agent?, signal }`
  (`dsh-tools/lib/types/index.d.ts:766`).
- **0.2.2-rc.1**: `execute(input: ToolBatchInput)` — a BATCH
  `{ calls: readonly ToolCallBlock[], signal, agent?, toolSet?, log? }`, where
  `ToolCallBlock = { type: "tool-call", id, name, arguments: <RAW JSON STRING> }` and the answer is
  `ToolBatchResult = { results, additionalContexts, concluded }`
  (`dsh-tools/lib/types/executor.d.ts:16-56`, `dsh-llm/lib/types/types.d.ts:92-99`).

Our call sends the single-call object, the executor throws internally and the harness wraps it as
`ToolBatchExecutionError("Tool batch execution failed")`. The MOUNT is fine; the in-process tool call is
not. The owning file is `packages/mpd-dsh-adapter-plugin/src/index.ts` (::`executeTool`) — **T3's
write scope**, so it is reported, not patched here (a fix that touches it from this task would collide
with T3's declared scope). The repair is a shape-adaptive shim in that one method: if
`Array.isArray(input.calls)`-style batch input exists → send `{ calls: [{ type: "tool-call", id: callId,
name, arguments: JSON.stringify(arguments) }], signal, agent }` and project `results[0]`; otherwise keep
the single-call path (0.2.1). `toolRuntime().execute` funnels through the same method and is fixed with it.
