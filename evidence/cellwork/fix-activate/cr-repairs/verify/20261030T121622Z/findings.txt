**Re-split of a pre-upgrade cell re-arms loops and rewrites frozen contracts.**

`state.ts` reads a record that has no `activatedLoops` as `{}`. For a cell activated before this change, `loopIds` therefore starts empty. The loop condition is now every code task in `deps.split.tasks`, not only `freshCode`. On the first re-split of such a cell, `mpd_verify_open` runs again for every kept code task. Each kept task's contract is also rewritten with a new loop id.

This creates duplicate loops. It also breaks the documented rule that a kept task's frozen contract is not rewritten. A verifier may already be reading that contract.

Skip a kept task when `activatedLoops` has no entry for it but its contract file no longer contains the placeholder that `withLoopId` replaces. That state means a loop was already armed.

**An in-flight revision still wedges the cell after a newer split is accepted.**

Trigger sequence:
1. Activation of revision 1 fails, so `activationInFlight` is 1.
2. The planner calls `cellwork_requirements update`.
3. The splitter resubmits and revision 2 is accepted. The stale-split refusal tells the caller to do this.
4. `state.splitRevision` is now 2.
5. `cellwork_activate` always refuses, because `activationInFlight` (1) differs from `acceptedRevision` (2).

The refusal text says to resume revision 1 "while it is still the accepted split". That revision is no longer the accepted split. The `revision` argument only acknowledges staleness of the accepted split. It cannot select revision 1. The only exit is `cellwork_stop`, which archives the cell and its board. This reintroduces the wedge this PR removes.

`materializeSplit` already reconciles against `activatedTasks`, so a newer revision can supersede the in-flight one. Allow a strictly greater `acceptedRevision` and journal the supersession. Keep the refusal for a lower revision.
