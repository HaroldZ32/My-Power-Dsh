## 5. PER-ROW ACCEPTANCE

### T-34 — `§5` (Skills & vendor) · friction · P2 · "a pre-commit hook that regenerates the lock"
- **DELIVERABLE:** `scripts/install-git-hooks.mjs` (NEW) installing a pre-commit guard for the corpus re-pin. **Allowed shapes:**
  (i) the hook regenerates the lock when the caller carries the captain's explicit marker, or (ii) the hook REFUSES the commit and
  names the exact remedy (`node scripts/repin-vendor.mjs --check` → the single `--write --i-know-this-is-the-captains-step` →
  `node scripts/verify-vendor.mjs`). **INVARIANT either way:** the hook must not be able to re-pin WITHOUT that marker — the helper's
  refusal flag exists so that a wave cannot re-pin mid-flight, and a hook that defeats it would be a regression dressed as a guard.
- **OBSERVABLE:** with a staged `skills/**` change and no lock change, the commit is refused and the output names the remedy; with the
  lock in sync, any commit proceeds untouched.
- **DECISIVE:** a driver builds a throwaway repo, stages a corpus tweak, runs the generated hook and asserts (a) non-zero,
  (b) the remedy text, (c) the lock file byte-unchanged; then stages the re-pin and asserts zero.
- **NEG CONTROL:** a staged NON-corpus change passes untouched; `install-git-hooks.mjs --self-test` must redden if the generated hook
  is empty or unwired, and must never write the repo's real `.git/hooks`.
- **EVIDENCE:** `evidence/gates/<slug>/<stamp>/` (both runs + the generated hook text).
