## 3. The guard — how a verifier SEES its decision

The row logs **one line per distinct decision** to the boot log:

```
[mpd-better-sidebar] mount guard: ENABLED - web plane present and no other layer mounts dsh-better-sidebar
[mpd-better-sidebar] mount guard: DISABLED - bundle layer @linxin666/dsh-web-all already mounts it in its own patch
[mpd-better-sidebar] mount guard: DISABLED - dsh-better-sidebar is itself a declared bundle layer
[mpd-better-sidebar] mount guard: DISABLED - patch layer <path> already mounts it
[mpd-better-sidebar] mount guard: DISABLED - no enabled @deepseek-ai/dsh-host-webserver entry in this composition
[mpd-better-sidebar] mount guard: DISABLED - dsh-better-sidebar is not resolvable from the profile node_modules
[mpd-better-sidebar] mount guard: DISABLED - guard threw <message>
```

(The `patch layer <path>` line is the REPAIR R1 addition: it names whichever of
`<profileDir>/cordis.patch.yml`, `$DSH_HOME/cordis.patch.yml` or a `--patch` overlay path
from `process.argv` mentions the package.)

`DISABLED` = the row does not mount; `ENABLED` = it does. The message names the clause,
so a verifier reads the decision AND the reason from the log, and greps the same log for
the fatal signatures (`duplicate prefix route`, `plugin(s) failed to load`,
`did not activate`, `pending (waiting for service`, `failed to apply loader entry`).

Second, independent witness: a probe row in an extra `--patch` layer logs
`SIDEBAR-PROBE {"total":…,"rows":[…],"web_entry":…}` where each sidebar entry appears as
`<id>|<literal-disabled|js-guarded|raw-enabled>|fiber=<true|false>` — the `fiber` flag is
the loader's own activation state, so "exactly one mount" is countable (`fiber=true`
appears exactly once). The probe expression is in
`scratch/run-compositions.mjs#PROBE_EXPR`.

Third: HTTP. `GET /?token=<token>` answers 303 and plants the auth cookie; with that
cookie `GET /` is 200 and its HTML lists `dsh-better-sidebar/client.js` in the composed
client-module bundle; that `/plugins/??dsh-better-sidebar/client.js…` URL answers 200
(≈870 KB module). `/sidebar/api` answers **405 with the plugin's own JSON**
(`{"ok":false,"error":{"code":"method-error"…}}`) when the plugin is mounted, and **404**
when it is not — that difference is the positive mount witness used in composition 5.

## 4. How to reproduce (the recipe this evidence came from)

```
SB=<evidence>/sandbox/<name>
mkdir -p $SB/dsh/profiles/<profile>/node_modules $SB/home/.dsh $SB/ws
cp ~/.dsh/settings.yaml ~/.dsh/.credentials.yaml $SB/home/.dsh/   # and into $SB/dsh/
# profile manifest: dsh.profile.bundles = the composition's layer list,
#                   dependencies = { "@mpd-dsh/mpd": "link:<bundle-dir>" }
ln -s <bundle-dir> $SB/dsh/profiles/<profile>/node_modules/@mpd-dsh/mpd
cd $SB/ws && DSH_HOME=$SB/dsh HOME=$SB/home dsh --profile <profile> --patch <probe.yml> --port <p> --no-open > $SB/boot.log 2>&1
```

* **Flag order matters**: `--patch` is a launcher flag and must come BEFORE the app's own
  flags (`--port`, `--no-open`), or the boot dies with `unknown option '--patch'`.
* stdio goes to a FILE, never a pipe (T-24); the harness runs each boot `detached` and
  kills the whole process group.
* The dsh-tui composition boots inside `tmux` (`pipe-pane` to a log + `capture-pane`),
  because the host refuses a piped stdout.
* Everything is sandboxed on ALL THREE axes: `DSH_HOME=$SB/dsh`, `HOME=$SB/home`,
  cwd=`$SB/ws` (AGENTS.md §7 — `DSH_HOME`/`HOME` do NOT isolate workspace state).
* **Composition 5 ("package absent") is built without mutating anything global**: a shadow
  bundle directory whose `package.json` is a copy of the repo manifest with
  `dependencies: {}` (every other key identical, and `packages/`, `presets/`, `skills/`,
  `extensions/`, … symlinked to the repo), linked into the sandbox profile in place of the
  repo. The row under test is therefore byte-identical to the shipped one, while the
  boot-time module fallback has nothing to materialize — exactly the state the guard's
  clause 1 must survive.
* `dsh plugin --profile web add .` cannot be exercised in this environment (pnpm's store
  index lives outside the workspace → `ERR_SQLITE_ERROR`), so the profiles are built by
  hand exactly as the captain's RED baseline does (its `result.json#how_to_reproduce`);
  the hand-built profile is byte-equivalent for the composition/load question and the
  repo's own QA cases build their sandboxes the same way.
* `bun add dsh-better-sidebar@0.19.0-alpha.1 --ignore-scripts` needed
  `BUN_INSTALL_CACHE_DIR` and `TMPDIR` pointing INSIDE the workspace (the sandbox's
  `/tmp` and `/root/.bun` are read-only). Result: 430 packages installed, lockfile
  written. `--ignore-scripts` means node-pty's native build did not run; every boot below
  still loaded the sidebar (`fiber=true`, routes registered) — the sidebar's lazy/optional
  handling of node-pty holds here, measured, and the GUI's terminal pane is the only
  feature that could need a built pty (out of scope for this criterion).

## 5. A packer defect this change uncovered and fixed

`scripts/pack-mpd.mjs#decouplePatch` rewrites `!!js` values whose scalar contains `": "`.
Its guard `(?!')` only recognised SINGLE-quoted scalars, so a double-quoted `!!js
"(expr)"` (the form this row needs, because the JS body is single-quote-heavy) was
re-wrapped as `!!js '"(expr)"'` — the expression became a STRING LITERAL, i.e. a packed
install would have shipped the row as always-disabled (a non-empty string is truthy) with
no log line. Fixed by making the lookahead quote-aware (`(?!['"])`); the packed artifact
is now byte-checked (composition 6 boots the packed copy and the guard logs ENABLED).

## 6. Bounds and non-goals (read before trusting the fix)

1. The guard's fs probe uses `process.getBuiltinModule('node:fs')` (the loader's `!!js`
   scope has no `require`/`createRequire`). On a Node older than the function's
   introduction the guard throws and returns DISABLED — a missing sidebar with one log
   line, never a dead boot. Every other throw path degrades the same way.
2. `scripts/install-profile.mjs` (the LEGACY dev/QA installer) writes the same row, but it
   does not install the package: on a legacy profile where `dsh-better-sidebar` is absent
   the guard disables the row and the boot stays green. The sanctioned user path is the
   bundle install (declaration + boot-time module fallback), which is what compositions
   1–3/6 exercise.
3. The duplicate-mount back-off reads every patch layer the loader composes — the declared
   bundle layers' `dsh.bundle.patch`, `<profileDir>/cordis.patch.yml`,
   `$DSH_HOME/cordis.patch.yml`, and every `--patch` overlay path recovered from
   `process.argv` (repair R1). It is deliberately OVER-APPROXIMATING toward DISABLED (a layer
   that merely mentions the package in a comment disables the row), and two things remain
   outside it: (a) a layer that mounts the sidebar from CODE rather than a patch — the
   loader's `duplicate prefix route` still fails loudly, which is the pre-existing ecosystem
   behaviour — and (b) an overlay handed to the CLI in a spelling neither `--patch X` nor
   `--patch=X`. The R3/R4 hardening is stated with the guard: the web clause is fail-closed
   (raw `options.disabled` must be absent or literally `false`), and self-exclusion is by
   package IDENTITY (`@mpd-dsh/mpd`), never by a substring of our own row id.
4. Author-run boots: this lane is the implementer, so its results are advisory by
   construction. The verification lane must re-run compositions 1–5 (and ideally 6) on the
   frozen revision hashes it measures itself.
